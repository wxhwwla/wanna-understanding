# ADR-0001：MVP 范围与技术选型

- **状态**：已接受
- **提出日期**：2026-06-17
- **最后更新**：2026-06-17

---

## 上下文

Wanna Understanding 项目刚启动，需要在短时间内验证「屏幕截图 → OCR → AI 分析 → 悬浮窗展示」的技术可行性。需要确定 MVP 的范围和技术选型，避免过度工程。

### 关键约束

- **时间**：MVP 应在 1-2 周内完成
- **技术**：团队成员最擅长 Python
- **目标**：验证端到端闭环可行性

## 决策

### 1. MVP 范围

**核心闭环（必须完成）**：

| 模块 | MVP 范围 | 说明 |
|------|----------|------|
| 屏幕捕获 | 截取活动窗口（VS Code / 记事本） | 暂不支持多显示器 |
| OCR | PaddleOCR + 基本预处理 | 暂不优化深色模式 |
| 触发 | 定时轮询（2s）+ 哈希比较 + 防抖 0.5s | 暂不监听事件 |
| AI 分析 | DeepSeek API + 结构化 Prompt + LRU 缓存 | 暂不流式输出 |
| 悬浮窗 | tkinter 无边框置顶 | 暂不跟随窗口 |

**不纳入 MVP**：
- 多 IDE 适配
- 用户配置 GUI
- 深色模式自动识别
- UI Automation 文本获取
- 流式输出
- 打包为 exe

### 2. 技术选型

| 组件 | 选型 | 替代方案 | 理由 |
|------|------|----------|------|
| 截图 | mss + win32gui | PIL.ImageGrab（慢） | mss 性能最好 |
| OCR | PaddleOCR | Tesseract（慢不准） | PaddleOCR 准确率最高 |
| AI API | DeepSeek | GPT-4o（贵） | 性价比最高 |
| 悬浮窗 | tkinter | PyQt5（依赖重） | tkinter 标准库零依赖 |
| 触发 | 轮询 + 哈希 | pynput 事件（复杂） | 轮询实现最简单 |

### 3. 架构风格

**管道架构（Pipeline）**：数据单向流动，每个模块独立可测。

```
Capturer → OCR → AI → UI
```

模块间通过数据类（`dataclass`）通信，不共享状态。这种设计使得：
- 每个模块可独立替换（比如 OCR 换 UI Automation）
- 单元测试容易（mock 上下游）
- 未来可分布到多线程/多进程

## 理由

1. **Python MVP**：团队最熟悉 Python，1-2 周可交付。先用 Python 验证所有风险点（OCR 准确率、AI 延迟、用户体验），再用 C#/Rust 重写核心。
2. **OCR 优先**：UI Automation 虽然更快，但需要针对每个编辑器编写适配代码。OCR 横跨所有编辑器，一次适配到处运行。
3. **DeepSeek API**：价格约为 GPT-4o 的 1/10，速度更快，对代码分析场景足够用。未来可随时替换为其他兼容 API。
4. **tkinter 悬浮窗**：零额外依赖。PySide6 虽然更美观，但 200MB+ 的依赖对 MVP 来说是负担。

## 影响

### 正面
- 快速验证项目可行性（2 周内见成果）
- 技术风险可控（所有组件都有成熟方案）
- 架构可演进（管道架构方便替换组件）

### 负面
- tkinter 悬浮窗不够美观（MVP 后可换）
- OCR 在深色模式下可能不准（MVP 后优化）
- 轮询方式 CPU 占用高于事件驱动（可接受）

### 风险
- OCR 对代码符号的识别率可能低于预期 → 对策：放大预处理 + 后处理符号映射表
- DeepSeek API 的稳定性 → 对策：客户端内置重试机制 + 切换至 OpenAI 兼容 API 的配置项

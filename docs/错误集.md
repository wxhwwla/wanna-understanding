### [ERR-001] venv 内 pip 因编码损坏无法使用

- **发现日期**：2026-06-17
- **严重程度**：SEV-MED
- **模块**：环境 / 工具链
- **状态**：已修复（提供重建脚本）

#### 现象

执行 `.venv\Scripts\pip.exe` 报 `SyntaxError: unterminated string literal`，堆栈指向 `pip\_vendor\rich\_emoji_codes.py`。

#### 原因

虚拟环境在非 UTF-8 环境下创建或更新，导致 site-packages 内文本文件损坏。

#### 修复方案

1. 双击运行仓库根目录 `修复venv.bat` 重建 venv；
2. 创建前设置 `$env:PYTHONUTF8 = "1"` 与 `chcp 65001`；
3. 若 pip 仍不可用，可用系统 Python：`pip install -t .venv\Lib\site-packages -e ".[dev,ocr]"`。

### [ERR-002] 截图区域 DPI 宽高重复缩放

- **发现日期**：2026-06-17
- **严重程度**：SEV-MED
- **模块**：`screen/region.py`
- **状态**：已修复

#### 现象

高 DPI 显示器上截图区域偏移或只截到部分客户区。

#### 原因

`ClientToScreen` 返回的 x/y 已是物理坐标，但对 width/height 再次乘以 `dpi_scale`。

#### 修复方案

`physical_rect()` 仅对 width/height 乘 DPI；x/y 保持原值。见 `WindowRegion.physical_rect()`。

### [ERR-003] VS Code/Cursor 开启 UIA 后仍走 OCR 且效果差

- **发现日期**：2026-06-17
- **严重程度**：SEV-LOW
- **模块**：`screen/text_extract.py`、设置 GUI
- **状态**：已修复（文档与 UI 提示）

#### 现象

`WU_USE_UIA=true` 后识别无改善或仍很慢。

#### 原因

Electron 编辑器控件树通常不暴露完整文档文本，UIA 返回空，自动回退 OCR。

#### 修复方案

对 VS Code/Cursor 保持 `WU_USE_UIA=false`；UIA 更适合传统 Win32 编辑器（如部分记事本、老版 IDE）。设置对话框已增加说明。

### [ERR-005] 流式 AI 报错 `'str' object has no attribute 'decode'`

- **发现日期**：2026-06-17
- **严重程度**：SEV-MED
- **模块**：`ai/stream.py`
- **状态**：已修复

#### 现象

配置 API Key 后，悬浮窗显示 `分析失败: 'str' object has no attribute 'decode'`，堆栈指向 `iter_sse_deltas`。

#### 原因

`httpx>=0.28` 的 `response.iter_lines()` 默认返回 `str`，旧代码按 `bytes` 调用 `.decode()`。

#### 修复方案

`iter_sse_deltas` 同时兼容 `bytes` 与 `str` 行（见 `_line_to_text`）。

### [ERR-007] 蓝角/底边/右边缩放热区无法拖拽

- **发现日期**：2026-06-17
- **严重程度**：SEV-MED
- **模块**：`ui/overlay.py`
- **状态**：已修复

#### 现象

「拖蓝色角缩放」不起作用，用户无法通过拖拽右下角蓝色方块或底边/右边来缩放悬浮窗。

#### 原因

1. 热区太小：蓝角仅 20×20px，底边/右边仅 8px，难以精准点击
2. `Text` 控件绑定了 `<Button-1>` 拖拽事件，与缩放热区的 Frame 控件存在事件竞争
3. 无日志记录，无法获知用户尝试操作时的实际行为

#### 修复方案

1. 热区增大：蓝角 20→28px，底边/右边 8→12px
2. 移除 `Text` 控件的拖拽绑定（仅标题栏可拖拽移动），避免事件拦截
3. 修正无效光标名：`"size_s"`→`"sb_v_double_arrow"`，`"size_we"`→`"sb_h_double_arrow"`
4. 拖拽和缩放事件均加入 debug 日志

### [ERR-008] Trae 编辑器 OCR 识别率极低

- **发现日期**：2026-06-18
- **严重程度**：SEV-HIGH
- **模块**：`ocr/profiles.py`、`ocr/preprocess.py`、`ocr/engine.py`
- **状态**：已修复

#### 现象

OCR 仅识别出 20-30 个字符（如 `6，55`），无法提取有效代码，反复提示"未识别到有效代码"。

#### 原因

1. Trae（基于 VS Code 的 IDE）窗口标题含 "Trae" 但未被 `detect_editor_profile` 识别，回退到 `generic` 配置（放大系数 2.0×，无固定二值化阈值）
2. 自适应阈值用中位数（像素 50% 分位），但代码文字仅占 ~25% 像素，中位数偏向白色背景，阈值过高导致文字被二值化为白色而消失
3. 置信度阈值 `min_confidence=0.5` 过高，EasyOCR 对代码特殊符号置信度偏低，大量识别结果被丢弃

#### 修复方案

1. 新增 `trae_dark` profile（继承 `vscode_dark` 的 2.5× 放大 + 0.72 裁剪比）
2. `detect_editor_profile` 增加 `"trae" in title` 检测分支
3. 自适应阈值从 50th（中位数）改为 **25th 百分位**，聚焦属于文字的深色像素
4. `min_confidence` 从 **0.5 降到 0.3**
5. OCR 模块各步加入 debug 日志（原始项数、置信度、最终字符数）

### [ERR-009] 悬浮窗死机：`_tkinter.TclError: bad cursor spec`

- **发现日期**：2026-06-18
- **严重程度**：SEV-HIGH
- **模块**：`ui/overlay.py`
- **状态**：已修复

#### 现象

应用启动后立即闪退，无任何错误提示（`pythonw` 模式不可见）。

#### 原因

`"size_s"` 和 `"size_we"` 是 X11 光标名，在 Windows Tk 上不存在。创建 Frame 时设置 `cursor="size_s"` 立即抛出 `TclError`，导致整个进程崩溃。日志系统未建立时无法捕获此错误。

#### 修复方案

1. `"size_s"` → `"sb_v_double_arrow"`（垂直双向箭头，Windows 原生）
2. `"size_we"` → `"sb_h_double_arrow"`（水平双向箭头，Windows 原生）
3. `"size_nw_se"`（↘ 光标）保留不动（Windows Tk 支持）
4. 建立 `logger.py` 日志系统，hook tkinter/threading/sys 未捕获异常

### [ERR-010] 中文显示乱码：Consolas 字体缺少中文字形

- **发现日期**：2026-06-18
- **严重程度**：SEV-HIGH
- **模块**：`ui/overlay.py`、`ui/history_dialog.py`
- **状态**：已修复

#### 现象

悬浮窗和历史对话框中的中文显示为乱码或错字，如：
- "潜在Bug" → "獣Bug"
- "改进建议" → "改效进建议"
- "功能说明" → "功能班"

#### 原因

内容区字体设为 Consolas（等宽英文无衬线字体），**不含中文字形 CJK 表意文字**。tkinter 遇到中文字符时回退到系统后备字体，但后备匹配失败，导致字形替换错误。

#### 修复方案

1. 悬浮窗内容区字体：Consolas 13pt → **Microsoft YaHei 13pt**（完整中文字形）
2. 历史详情区字体：Consolas 13pt → **Microsoft YaHei 13pt**
3. 标题栏用 `measure("测")` 检测字体是否存在，不存在则回退 `Microsoft YaHei`

### [ERR-012] HiDPI 屏幕窗口只占左上角 2/3（DPI 未感知）

- **发现日期**：2026-06-18
- **严重程度**：SEV-HIGH
- **模块**：`tcl_bootstrap.py`、`screen/region_confirm.py`
- **状态**：已修复

#### 现象

全屏窗口只覆盖屏幕左上角约 2/3，其余为黑屏。框选截图、悬浮窗均偏左上角。拖动框选区域也偏移。该问题仅在 DPI 缩放 >100% 的显示器上出现（如 150%/200% 缩放）。

#### 原因

Python 默认不是 DPI 感知（DPI-unaware）的进程。在 150% DPI 缩放下：
- `winfo_screenwidth()` 返回物理像素（如 2560）
- `winfo_width()` 返回逻辑像素（如 1707，＝2560/1.5）
- `-fullscreen` 创建逻辑尺寸窗口（1707×1067），物理上只占 2560×1600 的 67%
- 所有居中计算基于错误尺寸，导致偏移

#### 修复方案

1. `tcl_bootstrap.py` 模块级调用 `SetProcessDPIAware()`，在任何窗口创建前启用 DPI 感知
2. `region_confirm.py` 中所有尺寸计算基于 `canvas.winfo_width/height()`（启用 DPI 感知后即物理像素）
3. 截图改用 `mss` 直接截取主显示器（避免 `WindowRegion.physical_rect()` 重复 DPI 缩放）
4. 加上 `min(scale, 1.0)` 限制不放大超过原尺寸

### [ERR-013] OCR 英文代码识别质量差：符号混淆（_ ( ) 等大面积误识）

- **发现日期**：2026-06-19
- **严重程度**：SEV-HIGH
- **模块**：`ocr/engine.py`、`ocr/recognizer.py`、`ocr/preprocess.py`
- **状态**：已修复

#### 现象

OCR 输出严重变形，如 `from __future__ import` → `from future_- iport`、`sys` → `Sy5`、
`Path(__file__)` → `PathC_file-`。虽能识别代码位置，但字符级准确率极低，
导致 AI 分析回复"代码严重损坏，包含大量拼写错误和语法错误"。

#### 原因

1. **语言列表含 `ch_sim`（简体中文）**：默认 `["en", "ch_sim"]` 让 EasyOCR
   共享中英文模型权重，英文特殊符号（`_` `(` `)` `{` `}`）识别率大幅下降。
2. **放大不足**：`generic` 回退配置仅 2.0× 放大，小字号细节丢失；
   `_MAX_OCR_EDGE=1600` 限制导致有效放大被回削。
3. **后处理规则过少**：仅 6 条符号修复，缺少针对 Python 关键字和常见
   OCR 误识（`iport`→`import`、`Sy5`→`sys` 等）的修复。
4. **单行模式**：EasyOCR 默认逐行识别，缺乏行间上下文整合。

#### 修复方案

1. **默认语言改为纯英文** `["en"]`，移除 `ch_sim`。中英文混合代码需手动
   通过 `WU_OCR_LANG` 环境变量设定。
2. **generic profile 放大 2.0→2.5×**，`_MAX_OCR_EDGE` 1600→2400。
3. **增强后处理**：新增 18 条 Python 关键字/符号修复规则。
4. **启用 paragraph=True**：EasyOCR 段落模式，按段落合并文本行。
5. **二值化性能优化**：`Image.point()` 替代纯 Python 像素循环（快 100×）。
6. **`_parse_raw` 处理 None 置信度**：paragraph 模式下置信度为 None 时直接保留。

### [ERR-014] AI API 频繁 SSL 握手超时 + 心跳消息误导

- **发现日期**：2026-06-19
- **严重程度**：SEV-HIGH
- **模块**：`ai/client.py`、`config.py`、`analysis_coordinator.py`
- **状态**：已修复

#### 现象

分析失败：`_ssl.c:1003: The handshake operation timed out`（60 秒超时）。
同时悬浮窗一直显示"正在识别代码…"即使实际上已进入 AI 调用阶段。

#### 原因

1. 默认 `request_timeout=60s` 对某些网络环境下 DeepSeek API 的 SSL 握手不够用
2. OCR 后台线程的心跳函数使用固定文案，不区分 OCR 和 AI 阶段

#### 修复方案

1. **超时 60s→120s**：`config.py` 默认 `request_timeout` 从 60 改为 120 秒
2. **心跳分阶段**：`analysis_coordinator.py` 增加 `phase` 可变引用，
   AI 阶段开始前设为 `"AI"`，心跳文案变为"正在调用 AI 分析"

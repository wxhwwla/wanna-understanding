## 二、模块详细设计

### 2.1 屏幕捕获模块 (`src/wanna_understanding/screen/`)

#### 目标
定时或事件驱动下快速截取指定窗口的图像。

#### 选型理由

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|:----:|
| `mss` | 极快（纯 C 实现）、跨平台、Python 绑定良好 | 不支持直接截取子窗口 | ✅ 主方案 |
| `PIL.ImageGrab` | 标准库、简单 | 慢（纯 Python），不支持多显示器 | ❌ |
| `win32gui` + DC | 灵活、可截任意窗口、DPI 感知 | 代码复杂 | ✅ 辅助 |
| D3D / DXGI | 最快、最低延迟 | 复杂、需 C++/C 扩展 | 未来 |

#### 关键设计

```python
class ScreenCapturer:
    """截图抽象层，默认使用 mss 实现，支持全屏和指定窗口。"""

    def capture(self, region: WindowRegion | None = None) -> Image:
        """截取指定区域；region=None 时截取全屏。"""

    def capture_window(self, hwnd: int) -> Image:
        """截取指定窗口句柄的客户区。"""
```

**DPI 适配**：必须获取目标窗口的 DPI 缩放比例，将逻辑坐标转换为物理像素：
```
physical_rect = logical_rect * dpi_scale
```

```python
class WindowRegion:
    """区域值对象，封装矩形坐标并处理 DPI 缩放。"""

    hwnd: int           # 窗口句柄
    x: int              # 逻辑坐标
    y: int
    width: int
    height: int
    dpi_scale: float    # 自动获取

    def physical_rect(self) -> tuple[int, int, int, int]:
        """返回 DPI 补偿后的物理像素坐标。"""
```

**实际实现说明**：`center_crop()` 自动裁剪已被**手动框选**取代。
用户在全屏截图上拖动虚线框选代码区域（`region_confirm.py`），
同一窗口复用上次选区，窗口切换后需重新框选。

#### 性能目标
- 单次截图时间：**< 50ms**
- 截图频率：最高 **每 2 秒一次**

### 2.2 OCR 模块 (`src/wanna_understanding/ocr/`)

#### 目标
从截图中准确提取代码文本，尤其要处理好特殊符号（`() => {} #`）、缩进和语法高亮背景。

#### 选型理由

| 方案 | 准确率 | 速度 | 结论 |
|------|:------:|:----:|:----:|
| **EasyOCR** | ⭐⭐⭐⭐ | ⭐⭐⭐ | ✅ 当前主力（复用 endfield 封装） |
| Tesseract | ⭐⭐⭐ | ⭐⭐ | ❌ 慢且不准 |
| PaddleOCR | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 曾评估，已不采用 |
| TrOCR | ⭐⭐⭐⭐⭐ | ⭐⭐ | 未来 |
| Windows.Media.Ocr | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | C# 迁移目标 |

#### 预处理管线

```python
class ImagePreprocessor:
    """图像预处理管线，链式调用。"""

    def upscale(self, image: Image, factor: float = 2.0) -> Image:
        """放大 2-3x，提升小字号 OCR 准确率。"""

    def grayscale(self, image: Image) -> Image:
        """转为灰度。"""

    def binarize(self, image: Image, threshold: float | None = None) -> Image:
        """二值化，消除语法高亮背景干扰；默认使用 25th 百分位自适应。"""

    def invert(self, image: Image) -> Image:
        """反色（深色模式：白字黑底 → 黑字白底）。"""

    def process(self, image: Image, is_dark_theme: bool = False) -> Image:
        """执行完整预处理管线。"""
```

**说明**：`remove_non_code_area()` 已不再需要——由**手动框选**（region_confirm.py）
替代自动区域裁剪。二值化阈值默认为自适应 25th 百分位（针对代码文字仅占屏幕 ~25%
的实际情况，避免文字被二值化为白色而消失）。

#### 后处理策略

```
OCR 原始输出：       "def f1 (x):\n    return x**2"
    ↓ 特殊符号校正
    ↓ 缩进修复（基于前一行的缩进推断）
    ↓ 去重（相邻行相同内容可能是误识别）
校正后输出：         "def foo(x):\n    return x ** 2"
```

#### 难点解决

| 难点 | 对策 |
|------|------|
| 语法高亮背景干扰 | 二值化 + 反色消除色块干扰 |
| 小字号代码 | 放大 2-3x 后再 OCR |
| `_` `*` `->` 等特殊符号 | 后处理符号映射表 |
| 缩进丢失 | 根据每行左侧空白推断缩进层级 |
| 行号 / 状态栏文字混入 | 手动框选 + profiles 行号列裁剪 |

#### 性能目标
- 单次 OCR 时间：**< 500ms**（含预处理）
- 准确率：**> 95%**（常见编辑器默认字体）

### 2.3 触发模块 (`src/wanna_understanding/trigger/`)

#### 目标
智能检测用户何时「看完了一段代码」，避免在滚动过程中频繁触发分析。

#### 方案：轮询 + 哈希比较

```python
class ContentWatcher:
    """监控目标窗口内容变化。"""

    POLL_INTERVAL = 2.0  # 秒

    def __init__(self):
        self._last_hash: str = ""
        self._last_change_time: float = 0.0

    def poll(self) -> bool:
        """
        轮询检测窗口内容是否变化。
        返回 True 表示内容已变化且已稳定（防抖期已过）。
        """
        current = self._capture_and_hash()
        if current == self._last_hash:
            return False
        self._last_hash = current
        self._last_change_time = time.time()
        # 进入防抖等待
        return False  # 等待防抖确认

    def has_settled(self) -> bool:
        """防抖：确认内容已稳定超过阈值。"""
        return (time.time() - self._last_change_time) > DEBOUNCE_DELAY
```

#### 防抖调度逻辑

```
时间轴：
  用户滚动 → content_hash 变化 → 计时器重置
  用户继续滚动 → hash 变化 → 计时器重置
  用户停止 → 0.5s 无变化 → 触发分析
  窗口切换 → hash 变化 → 计时器重置 → 0.5s 无变化 → 触发分析
```

```python
class DebounceScheduler:
    """防抖调度器，管理分析任务的触发时机。"""

    DELAY = 0.5  # 防抖延迟（秒）

    def schedule(self, callback: Callable) -> None:
        """安排一次分析：取消之前的等待，重新计时。"""

    def _on_settled(self):
        """防抖结束，执行回调。"""
        self._callback()
```

#### 窗口切换检测

```python
def get_foreground_window_info() -> tuple[int, str]:
    """获取当前活动窗口的句柄和标题。"""
    hwnd = win32gui.GetForegroundWindow()
    title = win32gui.GetWindowText(hwnd)
    return hwnd, title
```

当活动窗口切换时，立即清空缓存并触发新分析。

#### 性能目标
- 轮询间隔：2 秒
- 防抖延迟：0.5 秒
- CPU 占用（空闲时）：**< 1%**
- 用户感知延迟（滚动停止到结果展示）：**1-2 秒**

### 2.4 AI 分析模块 (`src/wanna_understanding/ai/`)

#### 目标
将代码发送给大模型，获得结构化分析结果：「功能说明」「潜在 Bug」「改进建议」。

#### 选型理由

| 方案 | 价格 | 速度 | 质量 | 结论 |
|------|:----:|:----:|:----:|:----:|
| **DeepSeek API** | 极便宜 | 快 | ⭐⭐⭐⭐ | ✅ MVP |
| OpenAI GPT-4o | 较贵 | 快 | ⭐⭐⭐⭐⭐ | ⭐ 备选 |
| Claude API | 中等 | 快 | ⭐⭐⭐⭐⭐ | ⭐ 备选 |
| 本地模型 (Qwen) | 免费 | 慢 | ⭐⭐⭐ | 远期 |

#### Prompt 工程设计

**系统 Prompt**（角色设定）：

```
你是一个资深的代码审阅员。
你的任务是分析用户提供的代码片段，并给出结构化的反馈。

注意：
1. 只分析代码，不要评价代码风格或格式
2. 如果代码有严重错误或潜在 bug，请明确指出
3. 如果代码正确但可以改进，给出具体建议
4. 如果看不出功能或无法分析（如代码过于碎片化），直接说“无法确定”
5. 保持简洁，每个部分不超过3句话
```

**用户 Prompt**（每次发送）：

```
请分析以下代码：

```
{代码文本}
```

请按以下格式回复：
功能说明：[一段话概括这段代码的功能]
潜在 Bug：[列出可能的 bug 或逻辑错误；无则写"未发现明显 bug"]
改进建议：[列出改进建议；无则写"暂无"]
```

#### 结构化输出解析

```python
@dataclass
class AnalysisResult:
    code_hash: str          # 代码 SHA256
    summary: str            # 功能说明
    bugs: list[str]         # 潜在 Bug 列表
    suggestions: list[str]  # 改进建议列表
    raw_response: str       # API 原始回复（调试用）
    timestamp: float        # 分析时间
```

#### 缓存设计

```python
class ResultCache:
    """基于 LRU 策略的 AI 结果缓存。"""

    MAX_SIZE = 100  # 最多缓存 100 条

    def __init__(self, max_size: int = MAX_SIZE):
        self._cache: OrderedDict[str, AnalysisResult] = OrderedDict()

    def get(self, code_hash: str) -> AnalysisResult | None:
        """获取缓存的 A 分析结果。"""
        if code_hash in self._cache:
            self._cache.move_to_end(code_hash)
            return self._cache[code_hash]
        return None

    def put(self, code_hash: str, result: AnalysisResult) -> None:
        """缓存分析结果。"""
        self._cache[code_hash] = result
        if len(self._cache) > self.MAX_SIZE:
            self._cache.popitem(last=False)
```

#### 性能优化策略

| 策略 | 效果 | 实现 |
|------|------|------|
| **缓存** | 相同的代码不重复调用 API | SHA256 → LRU Cache |
| **防抖** | 滚动过程中不触发，减少 90% 调用 | `DebounceScheduler` |
| **局部发送** | 只发送 20 行代码，减少 token | `trim_to_context()` |
| **流式输出** | 边生成边显示，减少等待感 | `stream=True` API 参数 |
| **预加载** | 光标在代码上方停留时预分析 | 未来功能 |

#### token 消耗估算

```
假设：
- 每次发送 ~20 行代码 ≈ 500 tokens（含 Prompt）
- AI 回复 ≈ 200 tokens
- 每次分析总计 ≈ 700 tokens

场景：
- 每分钟分析 1 次（防抖后）
- 每小时 ≈ 42,000 tokens
- 每天（8h）≈ 336,000 tokens

DeepSeek 价格（约 1元/1M tokens）：
- 每天 ≈ 0.34 元
- 每月 ≈ 10 元
```

### 2.5 悬浮窗模块 (`src/wanna_understanding/ui/`)

#### 目标
在代码旁边显示一个无边框、半透明、置顶的悬浮窗，不干扰用户操作。

#### 选型理由

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|:----:|
| **tkinter** | 标准库、轻量、足够 | 样式老旧、不美观 | ✅ MVP |
| PyQt5/PySide6 | 美观、功能强大 | 依赖笨重 | ⭐ 可选 |
| WPF (C#) | 原生 Windows 支持 | 需 C# | 迁移目标 |
| Webview2 | 美观、CSS 渲染 | 依赖 Edge | 未来 |

#### 关键设计

```python
class OverlayWindow:
    """无边框置顶悬浮窗。"""

    WIDTH = 400
    HEIGHT = 300
    OPACITY = 0.85
    FONT_SIZE = 11

    def __init__(self):
        self.root = tk.Tk()
        self.root.overrideredirect(True)     # 无边框
        self.root.attributes("-topmost", True) # 置顶
        self.root.attributes("-alpha", 0.85)  # 半透明
        self.root.configure(bg="#1e1e1e")    # 暗色背景

        # 内容区域
        self.text = tk.Text(
            self.root,
            wrap="word",
            bg="#2d2d2d",
            fg="#d4d4d4",
            font=("Consolas", 11),
            relief="flat",
            borderwidth=0,
        )
        self.text.pack(fill="both", expand=True)

        # 绑定拖拽
        self.text.bind("<Button-1>", self._start_drag)
        self.text.bind("<B1-Motion>", self._on_drag)

    def show_near(self, window_rect: tuple[int, int, int, int]) -> None:
        """在目标窗口旁定位。"""
        x = window_rect[2] + 10  # 窗口右侧 10px
        y = window_rect[1]       # 顶部对齐
        self.root.geometry(f"{self.WIDTH}x{self.HEIGHT}+{x}+{y}")
        self.root.deiconify()

    def update_content(self, result: AnalysisResult) -> None:
        """更新显示内容。"""
        self.text.delete("1.0", "end")
        self.text.insert("end", f"📋 {result.summary}\n\n")
        if result.bugs:
            self.text.insert("end", "🐛 潜在 Bug:\n")
            for bug in result.bugs:
                self.text.insert("end", f"  • {bug}\n")
            self.text.insert("end", "\n")
        if result.suggestions:
            self.text.insert("end", "💡 改进建议:\n")
            for s in result.suggestions:
                self.text.insert("end", f"  • {s}\n")
```

#### 主要功能

| 功能 | 实现 |
|------|------|
| 无边框置顶 | `overrideredirect(True)` + `attributes("-topmost", True)` |
| 半透明 | `attributes("-alpha", 0.85)` 设置可配置 |
| 拖拽移动 | 标题栏拖拽（Text 区域不拦截拖拽事件） |
| 缩放 | 拖蓝角/底边/右边缩放，热区 12-28px |
| 窗口跟随 | `show_near()` 定位到编辑器右侧，屏幕边缘自动翻转 |
| 自动冻结 | 分析完成后 2s 自动冻结，Alt+Shift+F 解冻 |
| 快捷键 | Alt+Shift+H 显隐 / J 历史 / O 设置 / F 冻结 |
| 中文显示 | Microsoft YaHei 13pt 字体（支持 CJK） |
| 流式刷新 | 边生成边展示，节流间隔可配置 |
| 历史浏览 | Alt+Shift+J 打开历史对话框，JSON 持久化 |
| 系统托盘 | pystray 右键：显示/隐藏、冻结、设置、退出 |
| 设置 GUI | Alt+Shift+O 打开，写入 `.env`，保存后立即生效 |

## 四、关键技术决策

### 4.1 OCR vs UI Automation

```
当前实现：
  ┌────────────────────────────────────────────┐
  │ OCR（EasyOCR）+ 可选 UIA 优先               │
  │ 优点：通用、编辑器 profiles 调优             │
  │ 缺点：OCR 慢；Electron 编辑器 UIA 通常无效   │
  └────────────────────────────────────────────┘

未来扩展：
  ┌────────────────────────────────────────────┐
  │ UI Automation（Windows Automation API）     │
  │ 优点：极快、无 OCR 错误、直接获取精确文本    │
  │ 缺点：仅 Windows、需适配不同编辑器控件树     │
  └────────────────────────────────────────────┘

结论：MVP 用 OCR 快速验证，后续用 UI Automation
      作为低延迟补充或替代方案。
```

### 4.2 轮询 vs 事件驱动

```
轮询（MVP）✅：
  - 实现简单
  - 每 2 秒检测一次哈希
  - CPU 占用可控（< 1%）

事件驱动（未来）：
  - 监听全局键盘/鼠标事件
  - 即时响应
  - 实现复杂（pynput / Windows 钩子）

结论：MVP 用轮询，后期叠加事件驱动
      减少轮询频率。
```

### 4.3 悬浮窗 vs OS 通知

```
悬浮窗 ✅：
  - 持续显示分析结果
  - 位置可控（在代码旁边）
  - 可展示结构化内容

OS 通知：
  - 一闪而过，不适合持续展示
  - 无法展示结构化内容

结论：悬浮窗是唯一合理的方案。
```

### 4.4 流式输出 vs 完整等待

```
流式输出 ✅：
  - AI 边生成边展示
  - 减少用户等待感
  - 实现略复杂（需要流式 API + UI 异步更新）

完整等待：
  - 实现简单
  - 但 2-3 秒白屏影响体验

结论：Phase 2 已实现流式输出（默认开启）。
```

## 六、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|:----:|:----:|------|
| OCR 对代码特殊符号识别率低 | 高 | 中 | 放大预处理、后处理符号映射表 |
| AI API 延迟不稳定（1-5s） | 中 | 高 | 缓存 + 流式 + 用户感知设计 |
| 不同编辑器/主题差异大 | 高 | 中 | `ocr/profiles.py` 多 IDE 配置 + 行号裁剪 |
| EasyOCR 在深色模式效果差 | 中 | 中 | 反色预处理、阈值自适应、`ocr/theme.py` |
| 用户隐私顾虑（截图 + 外发） | 中 | 高 | 开源透明、支持本地模型（远期） |
| 频繁 API 调用导致 Token 成本 | 低 | 中 | 缓存 + 防抖 + 局部发送 |

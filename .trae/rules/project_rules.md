## 会话接续

在对本仓库做任何代码修改、重构、或新增功能之前，必须先读取以下文档：

1. `docs/会话接续手册.md` — 了解当前项目状态、架构接缝和近期完成的工作
2. `docs/项目目标.md` — 了解项目的长远愿景和当前焦点
3. `docs/技术方案.md` — 了解详细模块设计和接口约定

- 即使对话历史中已有这些文件内容，每次新对话也必须重新读取
- 如果文件内容在对话过程中被更新过，下次修改代码前应重新读取

## 先行阅读

动手前（改代码、推 GitHub、加模块等），必须阅读以下文档：

| 文档 | 何时读 |
|------|--------|
| `docs/技术方案.md` | **首次编码前必读** — 模块设计、接口约定、数据流 |
| `docs/项目目标.md` | **每次对话开始时** |
| `docs/版本号说明.md` | 修改版本号前 |
| `docs/操作指令集.md` | 改代码或推 GitHub 前 |
| `docs/代码结构规范.md` | 结构性重构或新增模块前 |
| `docs/错误集.md` | **每次报告 Bug 或问题时** |
| `CONTEXT.md` | 领域术语 |
| `docs/依赖说明.md` | 新增依赖前 |

## 错误集优先查阅规则

当用户报告 Bug、异常行为或提出改进请求时，**必须**：

1. **先查阅 `docs/错误集.md`**
   - 搜索是否已有类似问题的记录
   - 如有：参考修复方案
   - 如无：诊断后修复，并将新问题+修复方案追加到错误集
2. 修复完成后更新错误集文档
3. **禁止**：不查阅错误集就从头诊断已有记录的问题

## 任务完成收尾协议

所有任务项标记为「已完成」后，必须执行以下操作：

1. **更新文档**：如果本次变更影响了功能、结构、配置或操作流程，同步更新：
   - `docs/会话接续手册.md` — 文首日期、近期完成
   - `docs/操作指令集.md` — 新增命令、参数或流程
   - `docs/代码结构规范.md` — 新增/删除目录超限记录
   - `docs/错误集.md` — 新增 Bug 修复记录
   - `README.md` — 功能描述、目录列表
   - `CONTEXT.md` — 新增术语
2. **清理计划文件**：删除 `.trae/plans/当前任务计划.md`
3. **输出明确的任务总结**：列出已完成项 + 未完成项 + 当前暂存区状态
4. **向用户提问后续**：如"需要上传 GitHub 吗？"

**禁止**：修改代码后不同步更新相关文档，导致文档与代码不一致。

## 任务计划记录

开始处理任何代码修改、重构、或问题修复前，必须先将本次任务的计划（任务项、优先级、步骤）写入 `.trae/plans/当前任务计划.md`。

处理完毕后，必须删除该计划文件，表示任务已完成。

- 若任务分多次对话完成，每次新对话开始时先读取该文件了解进度
- 若计划在执行过程中发生变化，及时更新文件

## 默认开发流程

当用户请求功能实现、Bug 修复或代码变更时，默认走 `design-then-build` 工作流：

1. 先与用户沟通厘清设计
2. 再以 TDD 方式实现（测试先行，红-绿-重构）
3. 低风险操作（测试、代码编辑、安装依赖）可自动同意
4. 高风险操作（git push、破坏性命令）必须先问用户

## 严重程度标签

所有诊断信息必须标注严重程度标签：

| 标签 | 含义 |
|------|------|
| `[SEV-OK]` | 无问题 |
| `[SEV-LOW]` | 外观、风格、轻微重构 |
| `[SEV-MED]` | 逻辑 Bug、遗漏边界情况、潜在回归 |
| `[SEV-HIGH]` | 静默数据丢失、算术溢出、计算结果错误 |

## 并行执行

当一个任务可拆分为多个独立子任务时，应并行执行以缩短耗时。

始终将独立的工具调用（Read、Grep、Edit 等）合并到一条消息中。**不要将存在依赖关系的操作并行执行。**

## 推送与拉取 GitHub

### 核心原则：所有 Git 上传操作必须通过上传脚本

**所有涉及 git 暂存、提交、推送的操作，都必须通过 `python github_upload_module.py` 进行。**

- Agent **不得**直接执行 `git add`（即使只暂存文件）
- Agent **不得**直接执行 `git commit`
- Agent **不得**直接执行 `git push`
- 工作就绪后，Agent 告知用户应执行的命令和当前暂存区状态

### 推送（上传）

- **默认由人类执行上传**。Agent **不得**运行上传脚本，除非用户在**当前对话中明确要求**。
- 工作就绪但用户未要求发布时，**停下来**告知用户应执行的命令（`github_upload_module.py`，可选 `--minor` / `--no-bump` / `--dry-run`）。
- 如果用户明确要求上传：`python github_upload_module.py`（适当时添加 `--minor` 或 `--no-bump` 或 `--dry-run`）。
- `_VERSION` 版本号必须通过上传脚本更新。

### 拉取（下载）

- **不得**执行 `python github_download_module.py`，除非用户明确要求丢弃本地工作。
- 该脚本要求输入确认词 **`覆盖本地`**，会执行 `reset --hard` 和 `git clean -fd`。

## 禁止的操作（红线）

以下操作**绝对禁止**，除非用户在**当前对话中明确说出"执行"或"删除"等授权用语**：

| 操作 | 举例 | 原因 |
|------|------|------|
| **删除 Git 跟踪的文件** | `git rm`、`git rm --cached` | 永久删除仓库历史中的文件 |
| **删除工作区的文件/目录** | `del`、`rm -rf` | 可能误删重要代码或测试 |
| **丢弃未提交的更改** | `git checkout --`、`git reset --hard` | 不可逆地丢失未提交的代码 |
| **推送到远程仓库** | `git push`、上传脚本 | 影响其他协作者 |

## 文件编码

本项目所有 **`.py` 文件**使用标准文件头模板：

```python
# SPDX-License-Identifier: AGPL-3.0

"""模块一句话描述。"""
```

- 文本文件使用 UTF-8 编码（无 BOM）
- Python 3.11+ 不需要 `# -*- coding: utf-8 -*-` 声明

### venv 创建编码保护

**在创建或重建 venv 之前**，必须确保终端/进程编码为 UTF-8：

```powershell
$env:PYTHONUTF8 = "1"
chcp 65001 > $null
python -m venv .venv
```

### 写文件规则

1. **始终使用 `encoding='utf-8'` 打开文本文件**
2. **不得写入 BOM（Byte Order Mark）**

## Python 模块导入规范

### 核心原则

每个 Python 文件必须通过**显式、可追溯的 import 路径**被其他模块引用。

### 规则

| # | 规则 | 正确做法 | 错误做法 |
|---|------|----------|----------|
| 1 | **包内模块使用相对导入** | `from . import config` | `import config` |
| 2 | **包内交叉引用用相对导入** | `from .screen import capturer` | 绝对导入 |
| 3 | **入口脚本用绝对导入** | `from wanna_understanding import __version__` | 相对导入在 `__main__` 中失效 |
| 4 | **包目录必须有 `__init__.py`** | 每个子包都有 `__init__.py` | 命名空间包 |

### 导入排序

所有 `.py` 文件的 import 语句必须按以下**四组**顺序排列，组间用空行分隔：

```
组 0：from __future__ import annotations
组 1：标准库（os、sys、typing、pathlib 等）
组 2：第三方库（mss、httpx、pydantic 等）
组 3：本地应用（from . import xxx、from wanna_understanding import xxx）
```

## Python 代码风格规范

### 1. 公共 API 声明（`__all__`）

每个 `__init__.py` 必须声明 `__all__` 来确定模块的公共 API 边界。禁止隐式 exports。

```python
# 空包
__all__: list[str] = []
```

### 2. 文档字符串格式（Google 风格，中文）

**必须写** docstring 的情况：
- **公共 API**：被其他模块 import 的模块、类、函数
- **长函数**：函数体约 **>= 40 行**

**可不写** docstring 的情况：
- 模块内 `_` 前缀短 helper
- <= 3 行的 trivial wrapper

```python
def setup_logging(level: str | int | None = None) -> None:
    """初始化日志系统。

    参数:
        level: 日志级别（"DEBUG" / "INFO" / "WARNING"）。
    """
```

### 3. 自定义异常层级

- 异常类以 `Error` 后缀结尾
- 必须有文档字符串
- 特定构造参数使用仅限关键字参数（`*` 后）

### 4. 命名规范

- Python：`snake_case`
- 类名：`PascalCase`
- 常量：`UPPER_SNAKE_CASE`
- 注释语言：中文

### 5. 目录与文件规模

| 项 | 规则 |
|----|------|
| 目录宽度 | 直接子项 **<= 20（硬顶）**；**目标 <= 15** |
| 文件长度 | 业务 `.py` **<= 400 行**（硬顶 500） |

### 6. 测试组织规范

- 测试函数 `test_` 前缀 + `snake_case`
- 类内用 `TestXxx` 前缀
- Fixture 分三级（包级 conftest -> 目录级 conftest -> 模块级）
- 慢测用 `@pytest.mark.slow` / `integration` 标记

## 开发工作流（完整发布周期）

### 阶段一：规划与目标

1. **设定目标** — 明确本次要做什么。写入 `.trae/plans/当前任务计划.md`。
2. **先行阅读** — 按「先行阅读」规则读取所需文档。

### 阶段二：实现

3. **实现目标** — 按 `design-then-build` 工作流。

### 阶段三：文档同步

4. **更新文档** — 按「任务完成收尾协议」更新受影响的文档。

### 阶段四：验证

5. **确认测试** — `pytest` 全部通过
6. **确认代码检查** — `ruff check .` + `ruff format --check .` + `pyright src/` 全部通过

### 阶段五：发布

7. **输出任务总结** — 列出已完成项 + 未完成项
8. **向用户提问后续** — "需要上传 GitHub 吗？"
9. **用户执行上传** — `python github_upload_module.py`

## 规则同步

本仓库存在多个规则/配置文件的 Agent 使用：

| 文件 | 用途 | 适用环境 |
|------|------|----------|
| `.trae/rules/project_rules.md` | 主规则文件（最完整） | Trae IDE |
| `CLAUDE.md` | Claude Code 项目规则 | Claude CLI |
| `AGENTS.md` | 项目级 Agent 技能配置 | 通用 |

### 同步规则

1. **主文件**：`.trae/rules/project_rules.md` 是权威源。
2. **修改规则时**：先在 `project_rules.md` 中修改，立即同步到 `CLAUDE.md` 和 `AGENTS.md` 对应章节。
3. **不同步的内容**：IDE 特性相关的配置。
